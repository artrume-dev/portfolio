Intro

problem · approach · principles

The problem

Single-agent coding sessions lose the thread on larger apps. Requirements drift, quality varies from session to session, and nobody clearly owns the final decision.

The factory treats building software as a process with roles, shared language, quality checks and sign-off points, the way a good engineering team works, with agents doing the planning and building and people approving what carries risk.

Approach

Agents with clear roles

The work is split across agents for planning, building and reviewing, instead of one agent doing everything.

Partly autonomous

Agents run most of the loop. People approve the spec before any build starts, and any release that carries risk.

Every app tests the factory

Each build is also a test of the factory itself. Recurring feedback becomes a lint rule, a test or an agent skill.

Principles

People approve what matters
Agents plan and build; people sign off on the spec and on any release that carries risk.
Measure before trusting
Every system gets a test set and a quality bar before it's called done. New model versions are checked against real tasks, not leaderboards.
Limit what agents can touch
Tools get the narrowest permissions that work, with planning for prompt injection and data leakage.

Done by an agent

One build, step by step

  1. An agent interviews you about the idea and surfaces decisions you hadn't made yet.
  2. It writes the domain context and decision records, so every agent uses the same language.
  3. It writes a spec against that language.
  4. You approve the spec before any build starts.
  5. The work is cut into vertical slices, each a thin end-to-end piece, with a dependency graph.
  6. Each slice is built in its own worktree: failing test first, then code until it passes, an end-to-end check, then a commit. A progress file and feature flags carry state between sessions.
  7. A dual review checks coding standards and spec compliance. A failure sends the slice back to the build loop.
  8. Release is risk-tiered: low-risk slices merge automatically, the rest need your approval.
  9. The app ships.
  10. Production signals and factory evals are tracked: cost, defects that escaped review, and how often gates reject work.
  11. Recurring feedback is turned into a lint rule, a test or an agent skill, and the loop starts again.

Design decisions

Shared language before a spec
Agents drift when they name the same thing differently. Writing the domain context first keeps the spec, code and reviews consistent.
Vertical slices, not layers
Each slice works end to end, so progress is always testable and a failure is contained to one slice.
State outside the conversation
Long builds outlast any one session. A progress file and feature flags mean a new session picks up exactly where the last one stopped.
Risk decides who approves
Making a person approve everything slows delivery and dulls attention. Tiering by risk keeps human review for the changes that need it.
Evaluate the factory, not just the app
Cost, escaped defects and gate rejections show whether the factory itself is getting better from build to build.
