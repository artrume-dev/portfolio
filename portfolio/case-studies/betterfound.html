Intro

problem · product · decisions

The problem

Storefront search expects shoppers to know the right keywords. Someone looking for "a waterproof jacket for a beginner hiker under £150" gets nothing, or a page of irrelevant results, and leaves. The merchant never finds out what that shopper wanted.

Betterfound replaces the keyword box with a conversation grounded in the merchant's real catalogue, and turns every search into a signal about what customers want and what the catalogue is missing.

What it does

Embeddable product finder

A framework-free web component that drops onto any storefront, in floating, inline, discover, overlay or bar modes, streaming answers as they're written.

Searches the live catalogue

Queries the merchant's own store API at request time, so prices and stock are always current. No copy of the catalogue to drift out of sync.

Connects to any store

Shopify, WooCommerce, Magento, BigCommerce, Salesforce Commerce Cloud or a custom REST API, mapped onto one product model.

Catalogue gap insight

An analytics dashboard groups searches by intent and shows what shoppers asked for but couldn't find.

Key decisions

Two models, two jobs
Haiku plans the search with a forced tool call and Sonnet writes the answer. Planning is a short structured task, so the cheaper model keeps cost and first-token time down without weakening the reply.
Search the live catalogue, not a copy
The agent queries the merchant's API at request time. Vector search over products is kept as a separate, later track.
Test embeddings before trusting them
A spike on real queries showed embeddings caught typos and near duplicates, but scored two paraphrases of the same intent at only 0.52 similarity. Search grouping moved to Haiku clustering, which grouped them correctly.
Tenant isolation by construction
The merchant ID always comes from the signed-in session or the verified widget token, never from the request body.

What I'd do next

  • Semantic product search. Use the stored embeddings where the spike showed they work: matching products, not grouping searches.
  • Shared cache. Move the in-process cluster cache to Redis when the service scales beyond one container.
  • Sandbox-aware clicks. Add a sandbox flag to click events so preview traffic never skews click-through.

Calls a language model

How one search works

  1. The widget sends the shopper's message with the merchant's signed token. The server checks the token and loads the last 30 minutes of conversation from Redis.
  2. Haiku turns the message into structured search parameters: keywords, category, price range, tags, intents, sort order.
  3. The server queries every connected catalogue in parallel, maps the results to one product model and applies the merchant's include and exclude rules.
  4. If nothing matches, it relaxes the search step by step (wider price range, fewer tags) and labels the results as close alternatives.
  5. It records one analytics event in the background, so logging never slows the answer.
  6. Sonnet streams the reply alongside product cards, and may read a page on the merchant's site for specs. If no product genuinely fits, it adds a hidden marker that the server strips and records as a catalogue gap.
  7. A product-card click sends a non-blocking beacon that records the click.

Three kinds of "no result"

All three land in the zero-result insight, giving merchants a clear list of products customers want but can't find.

KindDetected by
Truly emptyNo product matched, even after relaxing the search
RelaxedResults only appeared after widening the price or dropping tags
IrrelevantThe model judged the results didn't genuinely fit the request

Analytics and the semantic layer

Shoppers type unique sentences, so "top searches" grouped by exact text is noise. Two mechanisms were tested on real data before choosing.

analytics      = SQL aggregates scoped by tenant and time window
trend          = (current − previous) / previous   for equal-length windows
click-through  = clicks / queries                  (safe when queries = 0)

embeddings     = voyage-3-lite, 512 dimensions, cosine similarity
  typos and near duplicates   0.93 – 0.97   merged correctly
  paraphrases of one intent   0.52          missed

clustering     = Haiku groups queries by intent → {label, members}
                 10-minute cache · on failure every query stays its own group

Embeddings are stored but deliberately not used for grouping; they're kept for future semantic product search.

Trade-offs and safeguards

Best-effort writes
Query events, click beacons, embeddings and catalogue-gap updates are all fire-and-forget. A logging failure never breaks the shopper's answer.
Long-running containers, not serverless
No cold starts, so in-process caches are viable. A shared Redis cache is the follow-up for scaling out.
Limited reach for the agent
The page-reading tool only fetches pages on the merchant's own domain, using signed requests and checks against server-side request forgery.
Every query scoped by tenant
Dashboard reads take the tenant from the session; widget endpoints take it from the verified token. Any tenant ID in the request body is ignored.
Tests against a real database
Behavioural tests are written first. Anything with real SQL runs against an in-memory Postgres, which caught grouping, middleware and clustering bugs that mocked tests missed.
