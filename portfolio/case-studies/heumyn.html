Intro

problem · product · decisions

The problem

Job hunting means scrolling through hundreds of listings across job boards and company career pages, most of which don't fit. Generic "match %" badges don't say why a job fits, and AI CV tools often make up experience the candidate doesn't have.

I wanted a tool that pulls jobs from where they're actually posted, ranks them with a score you can inspect, uses a language model only where it adds value, and rewrites a CV for a specific role while staying truthful.

It started as an MCP server with Claude Code sub-agents for my own job search. The same tools were later put behind a web API so anyone could use them without a terminal.

What it does

Job feed from the source

Scrapes Greenhouse, Lever, Ashby, Workday and SmartRecruiters, plus Adzuna, Reed, JobSpy, Google Jobs and Himalayas. It detects which applicant tracking system a company uses from its careers URL.

Explainable match scores

Every job gets a 0–100 score broken down by skills, title, domain and seniority, plus a requirement-by-requirement checklist.

Deep AI analysis

An LLM agent scores role, technical, company, growth and practical fit, calling tools for skill extraction, seniority and embedding similarity.

Truthful CV rewriting

A multi-step pipeline tailors and humanises the CV for a job, then checks the output against the original so nothing is invented.

Chat search

Ask in plain English, for example "remote senior React roles in London". A model turns it into filters, then results are ranked.

Employer side

Employers post jobs and the same engine ranks candidates, with an optional AI analysis per candidate.

Key decisions

Rules first, LLM second
Running a model on every scraped job is slow and expensive. A rule-based first pass handles the clear cases in milliseconds and only the uncertain ones go to the LLM. People choose between rule-based, hybrid and full-LLM modes.
MCP first, web second
Building the tools as an MCP server meant I could test them from Claude Code before any UI existed. The web API reuses the same services instead of reimplementing them.
Choose the model per task
Claude for nuanced analysis and writing, GPT-4o-mini for cheap structured filtering, embeddings for similarity, and an optional local model. Providers fall back automatically when one runs out of credit, and people can bring their own encrypted API keys.
Guard against made-up CV content
Early rewrites sometimes added experience the candidate didn't have. Four layers now prevent it: a strict prompt, a diff of the output against the source CV, better matching so rewrites aren't attempted for poor fits, and a warning before export.
Measure prompts, not just ship them
The job-analysis prompt is evaluated in Braintrust against human-labelled jobs for score accuracy, valid JSON, consistency, latency and cost.

What I'd do next

  • Learn the weights. Scoring weights are hand-tuned. The app already collects feedback on jobs, which could be used as labels to fit them properly.
  • Real semantic search. Store job embeddings in pgvector and blend cosine similarity with the current keyword ranking in chat search.
  • Smarter skill matching. Add synonyms and embeddings so "k8s" matches "Kubernetes".
  • Measure the filter. Compute true precision and recall of the job filter against user feedback, alongside the per-job confidence score.

Calls a language model

How a job is processed

  1. Jobs arrive from ATS scrapers, job-board APIs and employer postings, and are merged into one shape: title, description, requirements, tech stack, location.
  2. The candidate's context is built once per sync: skills from the active CV, years of experience, seniority, chosen domains and a minimum score.
  3. Every job gets a rule-based 0–100 score and F1 metrics in milliseconds.
  4. In hybrid mode, confident results skip the LLM: excluded jobs scoring under 20 and included jobs scoring over 80. The uncertain middle goes to the LLM, highest scores first, capped per sync.
  5. Scores, breakdowns and F1 metrics are stored and shown in the feed with a qualification checklist.
  6. When someone opens a job, the deep analysis agent runs and can call similarity and seniority tools.
  7. The person can save, track an application, or tailor their CV to that job.

1 · Rule-based match score

Fast, free and fully explainable. Each component is capped so no single signal dominates.

SignalMaxHow it's calculated
Skills5010 points per skill found in both the CV and the job (matched against a skill dictionary)
Domain20Domain alignment × 0.20; a flat 12 when no domain preferences are set
Title153 per role keyword in the title, 5 per key skill in the title
Seniority±15Penalty of 0, −5, −10 or −15 for a level mismatch
 
score     = clamp(0, 100, skills + title + domain + seniority)
include   = score ≥ 30   (10 when no preferences are set)

alignment = matched/total × 100 + transferable/total × 60 + mismatched/total × 20

Jobs with weak skills (under 15/50) and a weak title (under 3/15) are excluded early. Location, job type and industry are shown but don't change the score.

2 · Precision, recall and F1

A single score can hide a lopsided match: strong skills but the wrong role, or the right title with few skills. The engine also computes a precision-style and a recall-style score and combines them with a harmonic mean, which stays low unless both are good.

s = skills/50   t = title/15   d = domain/20

precision = 0.55·s + 0.30·t + 0.15·d
recall    = 0.50·(matched / job skills) + 0.25·(matched / CV skills)
          + 0.15·t + 0.10·d
F1        = 2·P·R / (P + R)
Honest caveat: this isn't F1 in the evaluation sense, where precision and recall are counted against labelled data. Here they're weighted blends of the same features, used as a per-job confidence score. Measuring the filter's real precision and recall against user feedback is on the roadmap.

3 · Embedding similarity

During deep analysis the CV and job text are embedded with OpenAI's text-embedding-3-small and compared with cosine similarity. The agent calls this as a calculate_similarity tool for role alignment and company fit.

similarity = (a · b) / (‖a‖ · ‖b‖)
score      = clamp(0, 100, similarity × 100)

4 · LLM deep analysis

Claude scores five categories and can call tools for skill extraction, seniority analysis and similarity while it reasons. It also receives the rule-based and F1 scores as context.

overall = 0.30·role alignment + 0.25·technical match + 0.20·company fit
        + 0.15·growth potential + 0.10·practical factors

Chat search ranking

A model first turns the query into structured filters, which are schema-checked; hard limits such as location and company are then enforced. Ranking itself is lightweight: keyword overlap with synonym expansion, no vector database.

score = 0.45·title + 0.23·description + 0.17·tech + 0.07·company + 0.05·location
      + boosts: exact phrase in title 0.12 · posted ≤7 days 0.06 · level 0.08
                remote 0.06 · job type 0.07

Trade-offs and limits

Two-speed matching
The feed uses the free rule-based score so it stays instant. Paid model analysis runs only when someone opens a role.
Cut prompt cost at the source
The LLM filter uses a fixed system prompt with job data passed as JSON, and builds the candidate profile once per sync instead of once per job, about 70% fewer prompt tokens.
No vector database yet
Ranking uses keyword overlap with synonyms so the stack stays simple until real usage shows a vector store is needed.
Treat model output and the web as untrusted
Parsed queries are schema-validated and length-capped. Scrapers only reach allow-listed ATS hosts, with checks against server-side request forgery.
Known limits
Exact-match skills miss synonyms, weights are set by hand, and the model computes its own weighted total. Each has a fix on the roadmap above.
