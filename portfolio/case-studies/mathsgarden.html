Intro

problem · product · decisions

The problem

Times tables stick with daily practice, and daily practice sticks with a reason to come back. The first version was a single HTML page with a prize reward, and it worked. But it kept everything in one browser, so progress on the tablet didn't show on the laptop, and clearing the browser would have wiped weeks of practice.

I wanted the same app, with the same look my kid already liked, working on any family device with shared progress, even offline, and without losing the history already built up.

What it does

Times tables and division

Tables 2 to 13, in rounds of 12 questions in random order, or mixed rounds of 20 facts.

Hints, not answers

After a wrong answer, a hint: for division, "t × ? = n"; for times tables, count up from the previous fact.

Stars and a daily goal

A star for every correct answer and a home-screen bar showing progress towards today's target.

Prize corner

Prizes unlock once the daily target is met, and one prize can be chosen per day. Parents set the prizes, each up to £5.

Parent view

Today's stats, daily progress, a breakdown by table and a CSV export, behind a parent PIN.

Any device, even offline

Installs to a tablet or phone home screen. Practice never waits for the network.

Key decisions

Keep what already works
The app was already loved, so the brief kept the UI and behaviour as they were and only replaced the storage underneath.
Migrate, never lose
Existing progress lived in one browser. A one-off import moves it to the database behind the parent PIN, and the local copy is kept rather than deleted.
Rules on the server, not the screen
The daily target and the one-prize-a-day rule are checked by the server and the database, so they can't be bypassed from the browser.
Collect only what's needed
It holds a child's data, so it stores a first name and practice answers and nothing else. No accounts, emails or analytics.
A tight brief, agreed up front
The scope, data model, endpoints and "done when" checks were written down before any code, with a clear out-of-scope list, so the agents built exactly that.

AI agent role

How an answer is saved

  1. My kid types an answer and presses Check. The app marks it right or wrong straight away; nothing waits for the network.
  2. The answer gets an ID created on the device and is written to a local IndexedDB queue.
  3. In the background (on load, every few seconds while online, and when the device reconnects) the queue is sent to the server in batches.
  4. The server stores each answer once. Sending the same batch twice is harmless because the device-made ID is used to skip duplicates.
  5. Stars, completed tables and today's count are calculated from the answers, so every device shows the same totals.

Safeguards

Two levels of access
A family passcode lets a device practise. A separate parent PIN, checked on the server for every prize, claim, settings and import request, protects the parent area.
Secrets stay out of the code
The passcode, PIN and session secret live only in Railway environment variables. Secrets are compared in constant time and login attempts are rate-limited.
Locked-down browser rules
Security headers and a content security policy with no inline scripts limit what the page can load or run.
Reviewed before release
A security agent reviewed auth, validation, headers and dependencies. It found no critical or high issues, and the dependency audit was clean.
