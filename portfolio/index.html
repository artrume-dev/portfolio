How I build

Agents that write and change things need limits. Agents plan and build; people sign off on the spec and on any release that carries risk. This is one run of the agent factory, from prompt to shipped app.

Agent factory · one build 11 steps · 2 human gates
  1. 01intent.grillagent interviews you; hidden decisions surfaced
  2. 02domain.contextCONTEXT.md + ADRs: shared language
  3. 03plan.specspec written against that language
  4. 04approve.specyou approve the spec before any build starts
  5. 05slice.ticketsvertical tracer-bullet slices, dependency graph
  6. 06build.loop ×Nper slice: worktree · TDD red→green · e2e verify · commit. A progress file and feature flags carry state across sessions
  7. 07review.dualstandards + spec compliance → fail loops to 06
  8. 08approve.releaserisk-tiered: low-risk slices auto-merge
  9. 09shipshipped app, e.g. A11yCheck
  10. 10operate.observeprod signals + factory evals (cost, escapes, gate rejects)
  11. 11learn.codifyrecurring feedback → lint rule · test · skill ↺ 01

People approve what matters

Agents plan and build; people sign off on the spec and on any release that carries risk. In enterprise tools, agents propose changes to data and a person applies them.

Measure before trusting

Every system gets a test set and a quality bar before it is called done. New model versions are checked against real tasks, not just leaderboards.

Limit what agents can touch

Tools get the narrowest permissions that work. I plan for prompt injection and data leakage, and keep a risk record for anything that reaches users.
