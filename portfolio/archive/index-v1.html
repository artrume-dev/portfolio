Agent factory

A system that turns a plain-language prompt into a working application, using a team of specialised AI agents.

Problem

Single-agent coding sessions lose the thread on larger apps: requirements drift, quality varies and nobody owns the final decision.

Approach

  • Split the work across agents with clear roles: planning, building and reviewing.
  • Kept the system partly autonomous, with human approval gates on the spec and on release.
  • Treated each app as a test of the factory itself, feeding lessons back into agent instructions.

Calls a language model

How one search works

  1. The widget sends the shopper's message with the merchant's signed token. The server checks the token and loads the last 30 minutes of conversation.
  2. A small, fast model turns the message into structured search parameters: keywords, category, price range, tags and intents.
  3. The server queries every connected catalogue in parallel, maps the results to one product model and applies the merchant's include and exclude rules.
  4. If nothing matches, it relaxes the search step by step (wider price range, fewer tags) and labels the results as close alternatives.
  5. It records one analytics event in the background, so logging never slows the answer.
  6. A larger model streams the reply alongside product cards. If no product genuinely fits, it flags this, and the event is marked as a catalogue gap.

Key decisions and trade-offs

Two models, two jobs
Haiku plans the search and Sonnet writes the answer. Planning is a short structured task, so the cheaper model keeps cost and first-token time down without weakening the reply.
Search the live catalogue, not a copy
The agent queries the merchant's own API at request time, so prices and stock never drift out of sync. Vector search over products is kept as a separate, later track.
Tested embeddings before trusting them
A spike on real queries showed embeddings caught typos and near duplicates, but scored two paraphrases of the same intent at only 0.52 similarity. Search grouping moved to Haiku clustering, which grouped them correctly, with a 10-minute cache and a safe fallback if the model fails.
Three kinds of "no result"
An empty search, a relaxed search, and the model judging results irrelevant all count as zero-result searches. Together they give merchants a clear list of products customers want but cannot find.
Tenant isolation by construction
The merchant ID always comes from the signed-in session or the verified widget token, never from the request body. Every analytics query is scoped by it.
Limited reach for the agent
The page-reading tool only fetches pages on the merchant's own domain, using signed requests and checks against server-side request forgery.
Tests against a real database
Behavioural tests are written first. Anything with real SQL runs against an in-memory Postgres, which caught bugs that mocked tests missed.

Calls a language model

How one search works

  1. The person types something like "remote design systems roles in London".
  2. A model turns it into structured fields: title, company, location, remote only, seniority. The output is checked against a strict schema before use.
  3. Hard limits such as location are applied, and recent results are served from cache.
  4. The app queries job APIs and company career pages, then merges the results into one format.
  5. Semantic ranking orders roles by relevance, with plain keyword matching as a fallback.
  6. The job filter scores each role against the person's CV profile and explains why it does or does not fit.
  7. The person sees a qualification breakdown, saves or applies, and can tailor their CV to that role.

Key decisions and trade-offs

MCP first, web second
Building the tools as an MCP server meant I could test them from Claude Code before any UI existed. The web API reuses the same services instead of reimplementing them.
Choose the model per task
A provider manager sends each task to Anthropic, OpenAI or a local model. Bulk filtering uses cheaper models, and an internal endpoint compares providers on the same jobs.
Cut prompt cost at the source
The job filter uses a fixed system prompt with job data passed as JSON, and builds the CV profile once per sync, not once per job. That reduced prompt tokens by about 70%.
Two-speed matching
The list view uses a free rule-based match so it stays instant. The paid model analysis runs only when someone opens a role.
No vector database yet
Ranking uses lightweight semantic scoring with a keyword fallback, so the stack stays simple until real usage shows a vector store is needed.
Treat model output and the web as untrusted
Parsed queries are schema-validated and length-capped. Scraping uses URL safety checks, and expensive endpoints sit behind Turnstile, quotas and rate limits.

How I build responsibly

Agents that write and change things need limits. These are the rules I design to.

People approve what matters

Agents plan and build; people sign off on the spec and the release. In enterprise tools, agents propose changes to data and a person applies them.

Measure before trusting

Every system gets a test set and a quality bar before it is called done. New model versions are checked against real tasks, not just leaderboards.

Limit what agents can touch

Tools get the narrowest permissions that work. I plan for prompt injection and data leakage, and keep a risk record for anything that reaches users.
